Prototype — roll-calc UI inside PlayerTile tie-break tiles

Issue #162: #160/#167 validated an enlarged, spell-aware RollCalculation design (icosahedron d20, boxed total, animated boon/bust badges) against RoundReveal.tsx's wide row only. This prototype drops that same design into PlayerTile.tsx's narrow tied-reroll tile — as used by TieBanner.tsx, laid out in its real grid-cols-[repeat(auto-fit,minmax(96px,1fr))] grid, squeezed inside a phone-width sleeve so the grid actually has to shrink tiles the way it would on a phone with 2–4 tied players. Three variants, four fixture scenarios each. Switch with the bottom bar or ←/→.

Variant A — #167's rich mode, dropped in unmodified

Exact same markup/sizing RoundReveal.tsx uses (20px d20, 34px boxed total, full-size animated badges) — no adaptation for the narrower tile.

1. Baseline tie — no spell effects (3 tied)

2. Disadvantage reroll — Slipped Spoon (2 tied)

3. Advantage reroll — Sugar Rush (2 tied)

4. Stacked flat/dice modifier + existing effect dots (3 tied)

Findings — Variant A

Calc line + boxed total fit?
No. At a 96–140px tile the die icon, discarded-die strike, modifier term, boxed total, and any dice-term icons wrap onto 2–3 lines and the boxed total's fixed 34px square forces the tile visibly wider than its unaffected neighbours in the same row (see scenario 4, tile 1 vs tile 3) — exactly the "forces the tile wider than its neighbours" failure the issue asked about.
D20 wireframe legible?
Borderline. At 20px the icosahedron edges are still individually resolvable, but crowded against the name/modifier text above it, it reads as visual noise rather than a die.
Animated badges vs effect dots?
Redundant and worse: the tile now carries three separate "this player has an effect" signals — the scrolling-gradient text badge, the boxed total's color is unaffected so no extra cue there, and the existing red/gold dot row below. Two signals for the same fact, competing for the same ~120px width.
Discarded die at this size?
Fits but reads as clutter — a struck-through number next to a live one, both tiny, is easy to misread as "two rolls" rather than "one kept, one discarded" without already knowing the convention from RoundReveal's wider row.
Multiple tiles animating side by side?
Yes, this is the worst of it — scenario 4's row has two independently-animating scrolling-gradient badges a few px apart, and their glow/pulse timing isn't synced, so the row reads as flickering rather than two clean individual cues.
Rejected as-is

Variant B — adapted compact rich mode

14px d20, no boxed total (bold inline total instead, matches bare mode's existing weight jump), discarded die collapsed to a tooltip-only "±" glyph, effect badge shrunk and de-scrolled (kept the pulse, dropped the horizontal gradient sweep) to cut down simultaneous motion.

1. Baseline tie — no spell effects (3 tied)

2. Disadvantage reroll — Slipped Spoon (2 tied)

3. Advantage reroll — Sugar Rush (2 tied)

4. Stacked flat/dice modifier + existing effect dots (3 tied)

Findings — Variant B

Calc line + boxed total fit?
Yes — dropping the boxed total for a plain bold inline number (same treatment bare mode already uses for its total) removes the one fixed-size element that was forcing tile width. All four scenarios keep tiles the same width as their unaffected neighbours.
D20 wireframe legible?
Just barely, at 14px — the icosahedron shape is still recognizably a d20 rather than a blob (this is exactly the "non-scaling-stroke" gotcha DieIcon.tsx already documents: default scaling stroke keeps edges crisp instead of fusing them at small sizes). It's decorative at this size, not something a player would read the vertex pattern of — but that matches how it's already used in RoundReveal too.
Animated badges vs effect dots?
Still two signals, but softened: dropping the scrolling gradient (keeping only the slow pulse/glow) makes the text badge read as "this effect is active" rather than fighting for attention, and it sits far enough below the dot row that they don't visually merge. Still recommend the follow-up issue ask whether the dot row should simply be suppressed for a player who already has a text badge showing here, rather than shipping both — that's a design call, not something this prototype can settle with fixture data.
Discarded die at this size?
Tooltip-only reads better than inline strike at this width — a small "±12" glyph with a native title tooltip ("Rolled 12, discarded for disadvantage") keeps the primary calc line to one row instead of wrapping to fit a second small number.
Multiple tiles animating side by side?
Much calmer — with the gradient sweep removed, two adjacent pulsing badges no longer read as flicker, just a soft synchronized-looking glow.
Recommended direction

Variant C — bare mode (current production, unchanged)

What PlayerTile/TieBanner already render today (RollCalculation's non-`rich` branch) — included as the baseline Variant A/B are being compared against, not a new proposal.

1. Baseline tie — no spell effects (3 tied)

2. Disadvantage reroll — Slipped Spoon (2 tied)

3. Advantage reroll — Sugar Rush (2 tied)

4. Stacked flat/dice modifier + existing effect dots (3 tied)

Findings — Variant C

Fits trivially (it's what's already shipped) but this is exactly the gap #162 opened against: a tied player mid disadvantage/advantage reroll gets no visual explanation at all of why their total came out the way it did — no discarded die, no card/caster attribution, nothing beyond the plain dots that were already there for any other active effect. Kept here only as the control.

Decision — for the follow-up implementation issue

  1. Ship Variant B's adaptation, not Variant A's unmodified drop-in: a distinct compact rendering path for PlayerTile's tile, not the same rich prop RoundReveal uses at its current sizing. Concretely: 14px d20 (down from 20px), no boxed total (bold inline number instead), discarded advantage/disadvantage die collapsed to a tooltip-only glyph instead of inline strikethrough, effect badge de-scrolled (pulse/glow kept, horizontal gradient sweep dropped) and sized down to ~8px text.
  2. Open question, not resolved here: whether the effect-dot row (effectBadges) should be suppressed for a player whose active effect is already shown via the new compact badge, to avoid showing the same fact twice. Needs a design call against real dot/badge combinations across more effect types than this prototype's fixtures cover — flag it explicitly in the follow-up issue rather than guessing.
  3. No production changes here — this file is fixture-only, standalone, and never wired into the app. The follow-up issue should copy Variant B's CSS/markup treatment (visible in this file's <style> block under .calc-compact / .discard-tooltip / .effect-badge.compact) as its starting point, the same way #160's own body carried its validated snippets forward.
